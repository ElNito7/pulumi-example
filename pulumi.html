Cloud infrastructure, written as ordinary code

Pulumi is an open source infrastructure as code tool. You describe servers, buckets, and networks in TypeScript, Python, Go, C#, or Java, and Pulumi works out what to create, change, or delete.

Deploy your first stack 
import * as aws from "@pulumi/aws";

// One S3 bucket, declared like any other object
const bucket = new aws.s3.Bucket("site-assets", {
  tags: { team: "web" },
});

export const bucketName = bucket.id;
import pulumi
import pulumi_aws as aws

# One S3 bucket, declared like any other object
bucket = aws.s3.Bucket("site-assets",
    tags={"team": "web"})

pulumi.export("bucket_name", bucket.id)

How a deployment runs

Your program never calls the cloud directly. It declares the resources you want, and the Pulumi engine compares that against what already exists.

  1. Write the program

    Declare resources as objects. Use loops, functions, and packages wherever they help.

  2. Preview the change

    pulumi preview runs the program and shows what would be created, updated, or deleted.

  3. Apply it

    pulumi up asks for confirmation, then makes the changes through each cloud provider's API.

  4. Record the state

    The result is saved to a state backend, so the next run knows exactly what is deployed.

The words you will meet first

Six ideas cover most of what you need to read a Pulumi project.

Project
A folder with a Pulumi.yaml file and your program. It names the runtime, such as Node.js or Python.
Stack
One deployed copy of a project. Teams usually keep a stack per environment: dev, staging, prod.
Resource
A single piece of infrastructure, such as a bucket, a database, or a DNS record.
Provider
A plugin that knows how to talk to one platform. There are providers for AWS, Azure, Google Cloud, Kubernetes, and many more.
State
Pulumi's record of what each stack has deployed. Store it in Pulumi Cloud or in your own bucket or local disk.
Config and secrets
Per-stack settings set with pulumi config set. Add --secret and the value is stored encrypted.

Compared with template-based tools

Tools built on YAML, JSON, or a dedicated configuration language solve the same problem. The difference is mostly in how you express the infrastructure.

Pulumi Templates and configuration languages
Language General-purpose languages your team already writes A format or language specific to the tool
Logic and reuse Loops, conditionals, functions, classes, and published packages Built-in constructs and the tool's own module system
Testing The unit test framework of the language you chose Tool-specific test and validation commands
Learning curve Easier for developers, steeper for people who don't program A smaller surface to learn, with less room to abstract

Terminal
# Install the CLI (macOS and Linux)
curl -fsSL https://get.pulumi.com | sh

# Create a project from a template
mkdir site && cd site
pulumi new aws-typescript

# Preview and deploy
pulumi up

# Remove everything when you are done
pulumi destroy
